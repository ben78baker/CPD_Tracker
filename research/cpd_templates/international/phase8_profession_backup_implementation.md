# Phase 8 · profession backup rehearsal

**22 November 2026.** Implements the approved follow-up to [the profession backup assessment](phase8_profession_backup_assessment.md) in a disposable Flutter rehearsal. The production entry point, legacy store, signing and minimum OS configurations remain unchanged. Production SQLite activation is disabled.

## Archive and privacy

The existing `.recordingbackup` stream and SHA-256 verifier now also accept a version 2 collection manifest. It identifies one collection and its source lineage. A scoped SQLite projection carries reachable immutable definitions and recipes, all layouts and record deletion flags, evidence relationships and approved CPD host state. It excludes unrelated professions, global preferences, store grants, drafts and migration handoff state. The historical CPD adapter retains and verifies the selected profession's report selections, targets, reporting periods and pinned bundle envelopes. Whole-store version 1 remains available in the earlier rehearsal. The new import route requires a single-collection archive.

Users may share a verified plain file or protect it with a password. The encrypted envelope uses the Apache-2.0 Dart `cryptography` library with Argon2id (19 MiB, two passes, one lane and a fresh 16-byte random salt) and AES-256-GCM. It authenticates the header as associated data, uses sequential 96-bit nonces with a separate per-file key, and divides the complete archive into 64 KiB chunks plus an authenticated final empty chunk. Only the envelope marker, salt and byte length are visible. File length and authentication are checked before an archive is considered for restore. The key is discarded after use. Passwords are transient, with no account, network request or password reset. Encryption runs in an isolate and streams evidence. The existing archive codec uses temporary plaintext in app-private cache while packaging or verifying and the rehearsal removes encrypted handoff copies after sharing and removes the remaining staging data when leaving the screen or at cold start. OS-level secure erase and independent cryptographic review remain public-release considerations. [OWASP password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [NIST AES-GCM](https://csrc.nist.gov/pubs/sp/800/38/d/final) · [Dart cryptography package](https://pub.dev/packages/cryptography)

File checksums detect accidental damage. Password protection also authenticates the encrypted content with the provided password. Neither route makes an archive a store receipt or identifies a publisher. User-selected external copies are outside the app's authority. Onboarding and rehearsal Settings describe storing external backups securely and the loss risk after uninstall, device loss or disk failure. The linked draft policy covers password recovery, plain files, OS-managed copies and statutory rights. [Proposed wording](phase8_profession_backup_assessment.md#wording-review-and-drafts)

## Import and ordinary save integrity

The existing profession overflow menu and shared Add Profession screen receive the rehearsal callbacks. The create flow displays unavailable source originals with their names and status and requires acknowledgement before sharing the remainder. The archive carries the original references and missing, damaged or unresolved status. A formerly managed original is checked against its saved fingerprint when available. A legacy original without a known hash can be verified from capture onward. Truncated or corrupted archive payloads are rejected. The restore screen shows the profession name, date, record and attachment counts, evidence gaps and verification outcome before confirmation.

Restore always opens the provider file read-only, rebuilds a verified candidate privately and confirms with a fresh local profession ID. Source lineage detects renamed files and re-exports. Active duplicates open the existing profession. Recoverably deleted duplicates lead to Deleted Professions. Permanent deletion releases the duplicate guard so the external file can restore that lineage again. Conflicting names can be corrected. Conflicting immutable definitions fail the import. There is no merge or replacement path.

New managed originals are flushed and published under a unique restore-attempt directory before the SQLite commit. Native directory synchronisation is checked before those paths can be referenced. The rehearsal verifies SQLite journalling and foreign keys when opening its recording database. It uses `DELETE/EXTRA` when available, with `WAL/FULL` for older SQLite engines that cannot enable `EXTRA`. Android API 24 exposed this difference and passed after the fallback was added. The collection, related rows, scoped host data and lineage commit together. After a failed or interrupted import, an exclusive cold-start check removes only attempt directories whose files have no collection or attachment references. A committed import is recognised once. Ordinary saves take no automatic full checkpoints. The prior checkpoint rehearsal is retained for historical tests. Verified migration snapshots and retention gates remain separate. [SQLite synchronous settings](https://www.sqlite.org/pragma.html#pragma_synchronous)

Historical records and the standard export route are available without verified template ownership. Access checks still apply to adding new activities with a paid template, layout editing, premium reports and catalogue updates. Adding a paid-layout activity checks ownership at commit. There is no grant in the portable graph and no entitlement mutation in import.

## Verification and release gates

The full Flutter suite passed **253 tests**. Static analysis reported the same 13 existing warnings and informational findings, including findings in untracked marketing output. New tests exercise authenticated streaming across block boundaries, wrong passwords, edited headers, moved chunks, corrupted final tags and truncation. The restore entry fits 320-pixel width and 170% text scaling across all six locales and eight accents.

The native suite ran against an iOS 18.5 simulator and Android API 24 and 34 emulators on an Apple M4 Pro, using separate debug application identifiers. It checked missing and damaged originals, a verified partial archive versus a corrupted one, storage-capacity rejection, synthetic rollback immediately before commit, immutable historical rules, preservation of a pre-existing unrelated tile, duplicate re-exports and repeat restore after permanent deletion. At restore it confirmed that the archived purchase state was absent and the CPD host refused new paid-layout activities. The external source digest remained unchanged. On Android API 34, the native UI smoke check opened backup from a profession tile and restore from Add Profession. It verified the partial-evidence confirmation, plaintext warning and password dialog with two secure input fields.

Both plain and password-protected files passed byte-identical transfer and import in both directions between iOS 18.5 and Android API 24. Android API 34 also imported the iOS files. The iOS leg exposed a race between renaming decrypted output and cleaning the staging directory. The corrected reader awaits publication before cleanup, and the reverse-transfer probe passed again.

The native harness then stopped the apps on iOS 18.5 and Android API 24 at the point where originals had been published but the SQLite transaction had yet to commit. Restart found the pre-existing profession intact and no partial tile. It removed the unreferenced restore-attempt directory and retried successfully into one new tile. The archive remained available for retry. Capacity rejection was injected at the preflight boundary. The test did not fill the device volumes.

## Follow-up safeguards

The follow-up binds field and choice checks to each record's effective layout. It seals the privately rebuilt SQLite database before review and checks it again before committing the import. It rejects unexpected journal data, invalid report selections and attempts to supply an entitlement through host data. Owned picker copies are explicitly released on completion and cancellation. Exclusive cold start reconciles the rehearsal's staging paths without deleting an external source. Signed physical tests still need to qualify OS/provider cache ownership, low storage, device interruptions and exports.
