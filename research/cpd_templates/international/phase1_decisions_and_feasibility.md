# Phase 1 architecture decisions and feasibility validation

**20 November 2026 · Checkout `425e6bb` · For approval before implementation**

## 1. Executive recommendation

**GO WITH CONDITIONS** for Phase 1. The agreed architecture is technically sound for a mobile-first, independently developed Flutter app. Keep the existing Flutter shell and use an internal plain Dart recording module. Use **the already locked `sqflite` 2.4.2** via one local SQLite repository adapter, with original attachment files outside SQLite. Keep CPD business rules in a host adapter. Preserve the existing free workflow using a default CPD layout. Users can adopt a profession template later.

Approve the identity and history model, migration and recovery contract, and parity release gate before writing production code. Host tests support the proposed transaction and data shapes. Native plugin operation on the supported iOS and Android minimums, an executable migration against synthetic legacy stores, and real PDF/CSV parity remain release gates.

**Decision status.** The module direction and safety constraints are agreed in the brief. The choices below are recommendations for final approval. This report develops the earlier [architectural review](architecture_implications.md) using the [Field Library](field_library.md), [reporting requirements](../reporting_requirements.md), [validation plan](validation_plan.md), and [initial catalogue](../initial_catalogue.md). The 60 library candidates are research input. NMC and HCPC lead the shortlist and support the need for controlled choices and evidence. Their scheme calculations and commercial work are outside Phase 1.

## 4. Module boundaries and persistence choice

```text
CPD Flutter shell and CPD host policy
  ├─ entry, targets, QR, navigation, profile, CPD reports
  ├─ Flutter form and editor presenters ─────┐
  ├─ SQLite / managed files / share adapters ┤
  └─ Read-only legacy source adapter ────────┤
                                             ▼
                                  Plain Dart recording module
                      collections · typed values · layout history
                     template recipes · validation · resolved queries
```

- **Recording domain.** Own collection and record identities, types, validated changes, templates, revision and applicability resolution, generic searches and report projections. It has no Flutter or CPD imports. Business dates and durations are optional generic fields. Terms such as profession, credited CPD, scheme, regulator, entitlement, app colours and organisation logo are host concerns.
- **Repository and file adapters.** Use a single transaction-oriented repository rather than one service per table. Keep path mapping, file IO, SQLite/package calls and import parsing at the boundary. Start with the known current search semantics and small scoped queries. Prefer ordinary indexes on collection/lifecycle and supported projections. Defer full-text and attachment-content indexing.
- **CPD host.** Map professions to collections and bind standard field roles. Retain CPD date rules, progress totals, target periods, the configurable 20-active-field limit, navigation and localisation. Retain QR/picker/share as UI adapters. Use existing PDF preparation and renderers at first, taking a frozen legacy-compatible projection. Keep the signed-off pricing, template ownership, editing entitlements and per-profession branding decisions outside the module and this implementation phase.
- **Practical extraction seams.** Keep a compatibility projection for `CpdEntry` consumers until forms, search, targets and exporters all use the new record view. Pass immutable evidence metadata to export classification instead of handing the renderer a live repository. Split the file reference resolver from its `BuildContext` wrapper. Route every record mutation, including delete/restore and attachment removal, through the same writer. Do not extract a package before this boundary has a second tested consumer. [Prior module review](architecture_implications.md#3-dependency-boundaries-and-package-strategy)

### Selected persistence approach

| Option | Compatibility and development trade-offs | Decision |
|---|---|---|
| **Existing sqflite 2.4.2** | Mobile native plugin uses OS SQLite. Transaction and version callbacks are suitable for one writer and tracked migrations. Constraint enforcement is available with per-connection foreign keys. Direct SQL keeps setup small. It needs explicit schema migration fixtures, a platform integration pass and an optional host test adapter later. | **Select.** Preserve the lockfile. Use basic SQL features and confirm on oldest supported OS versions. Run FK enablement before transactions, use the transaction handle for every statement, and keep filesystem work outside the SQL transaction. |
| Drift over SQLite | Typed queries, reactive streams and migration test support can help a larger query surface. Native and web paths have their own setup. It would add a runtime layer and typically code generation and build tooling. | Revisit if query or schema complexity demonstrates value. The plain Dart domain does not depend on the adapter choice. |
| Direct Dart `sqlite3` or `sqflite_common_ffi` | Host tests and broader native packaging options are attractive. Direct FFI brings a SQLite library/native build hook and its own thread or isolate choices. The companion FFI adapter can exercise the sqflite API on host when separately approved. Device behaviour still needs native tests. | Defer dependency changes. Use stdlib host SQL for this feasibility pass. Verify exact toolchain requirements before adopting either for tests or another platform. |
| Continue SharedPreferences | Lowest initial setup, but whole-list replacement and multi-key record/target updates leave no durable relationships or transactional migration authority. Its documentation advises against use for critical data. | Keep ordinary app preferences there. Migrate the record graph. |

The cached, locked platform sources mark iOS 12 and Android API 19 as plugin minima. iOS 15.6 is above that native floor. Android’s effective floor is the highest applicable app/Flutter/plugin requirement. Inspected metadata shows no new minimum imposed by this choice. Confirm the actual release toolchain, native database opening, FK configuration, upgrade paths and application Documents access on both supported floors. macOS registration is present. Any promise for Windows, Linux or web needs its own adapter and acceptance check. Keep path and database adapters replaceable for a second product. ## 5. Implementable logical model and version rules

Use relational identities and constraints for record ownership and evidence associations. Small immutable ordered configuration snapshots can use versioned payloads. Store sparse typed record values. Projections are rebuildable and updated with the source change. Avoid a separate SQL table for every validator or control setting.

| Entity | Identity, relationships and invariants |
|---|---|
| Collection | Stable portable ID, display name, deletion state and pointer to one current layout revision. A collection owns records and field instances. CPD stores optional profession metadata and target keyed to this ID. |
| Record | Stable portable ID, collection ID, immutable creation layout revision, update revision and deletion state. Keep legacy ID and source ordinal as provenance and deterministic ordering tie-breakers. Existing ID collisions do not collapse records. |
| Template and version | Stable recipe ID and immutable ordered version. Fields have stable recipe-local keys and definition references or inline user definitions. Record values and evidence stay on records. Applying a template creates an independent layout, with field keys remapped to collection instances. Apply tracked revisions only by explicit choice. |
| Catalogue definition and version | Stable namespaced ID, versioned type, validation, labels, help, search terms, scope, source metadata and effective choice list. Runtime fields carry snapshot settings and optional provenance. Later catalogue changes do not mutate existing instances. |
| Field instance and layout revision | Stable collection-scoped field ID. Revision contains ordered field configurations and a parent/revision number. Record history resolves effective definition and option version from its creation revision and later explicit historical extensions. Store applicability scope and retirement separately from the value. |
| Controlled choice | Persist stable option IDs in a specific choice set, and retain their relevant historical version. Same label is insufficient to match choices. Resolve historical labels after an option is retired. |
| Record value | Unique record/field pair, with exact typed payload or managed attachment links. Include the effective definition/choice version where needed to disambiguate. Reject cross-collection references. Distinguish absent, zero/false, explicitly cleared and inapplicable states. Dates are calendar days. Duration is integer minutes. Future exact quantities use a decimal representation plus an explicit unit and scale. |
| Evidence asset and association | Asset/reference ID, storage kind, original local locator or URI, name, availability and integrity metadata as applicable. A record/field link carries order. Managed originals are app-owned files. Shared assets remain until every eligible reference, including restorable rows and any pinned export, is released. |
| Migration and historical metadata | Source fingerprint, parser/migration versions, source ordinal and legacy key mapping, original raw snapshot, exception codes, completion marker. Keep unknown raw values recoverable. Scheme rule versions remain a separate future CPD layer. |

**Canonical fields.** The CPD adapter binds activity date, title, details, credited duration and evidence to designated stable field instances in the standard layout. The field value is authoritative. Protect activity date and credited duration semantics. A query column for date or minutes is derived and checked at commit. A template cannot replace a canonical binding by adding another field with the same label. The generic engine allows a collection with neither a date nor a duration and distinguishes CPD credited time from any additional duration. Preserve legacy date display and the current half-open target and inclusive export contracts.

| Change | Identity and history rule |
|---|---|
| Presentation and formatting | A new layout configuration suffices. An icon, placeholder, display date format or text presentation can change without rewriting values. Preserve historical formatting where needed to reproduce an approved report. |
| Field label or order | New layout revision, same field ID. Existing records retain original label/order for historical interpretation. The UI may show the current label as a separate hint. Ordering affects the complete tile. |
| Configuration | Same ID and new revision if values retain meaning. Examples include a narrower label length for future records, requiredness or adding options. Retain already stored values and do not apply new requiredness to unrelated historical edits. Option relabel/reorder keeps IDs where meaning is unchanged. |
| Type or meaning | New stable field ID if storage semantics, unit, cardinality, eligibility or interpretation changes. Keep the old version and its values. A short-to-long text presentation can share identity. A choice with revised semantics needs a new option ID, even if its label is unchanged. Explicit conversions require a separate reviewed process. |
| Removal from template or tile | New template version only affects future adoptions. A local retirement removes the field from new records in that collection. Populated retired fields remain readable and exportable, with original metadata and references retained. |
| Permanent deletion | Separate explicit confirmation against the current impact, including deleted-but-restorable records. Transactionally remove the intended values and links. Then reclaim app-owned bytes only after rechecking all references. Resolve backup and legacy-snapshot retention separately before authorising a purge feature. |

**Older records.** Resolve the creation revision plus explicit historical extensions. **Future records only** takes effect from the new creation revision, independent of a backdated activity date. **Include existing records** adds a blank applicable field by metadata, with no bulk write of empty values. Restored records keep the same identity and historical applicability. A draft Save checks the expected current revision, approved fields and final active count. Cancel or conflict leaves the current layout and original evidence intact. The CPD limit is 20 active fields including standard fields, with retired history and branding outside the count. [Editor and historical design](../../../docs/custom_fields_ui.md#5-drafts-historical-records-and-save)

## 6. Migration and recovery contract

| Step | Required contract and failure outcome |
|---|---|
| **Preflight and single authority** | Gate every writer during import, including rename, record restore, QR creation and evidence removal. Read raw preference keys directly, reload once at the boundary if needed to avoid stale caches, and snapshot the exact record list, counter, active/deleted names and targets under a versioned manifest. Leave profile and display preferences on their existing path. Check free space and destination writability. Create a fingerprint of the frozen input and inventory attachment paths and states without opening arbitrary external content or downloading links. |
| **Recovery snapshot** | Store a recoverable raw snapshot privately with integrity metadata and a verification timestamp. Keep input keys and managed originals in place during Phase 1. Treat original files as pinned for the migration recovery window. Recommend retaining the separate recovery copy through verified cutover and at least 30 days, with approval and a successful recovery rehearsal required before retiring any source data. Unresolved data keeps the relevant snapshot. No automatic original-file cleanup in the first migration release. |
| **Safe classification** | Map unambiguous names to stable collection IDs following observed legacy rules. Preserve raw labels, deletion state and targets. Keep orphans recoverable without making unrelated records visible. Assign separate IDs for duplicate legacy IDs using snapshot identity and source row position. Preserve both conflicting targets and hold cutover if the intended association cannot be established. Accept documented defaults for truly absent optional values. Impossible dates, non-integral or out-of-range time, unknown custom payloads and malformed rows keep their raw originals. Resolve ambiguity before activation or use an explicit, approved recoverable exception path. Never count an unparsed row as faithfully migrated. |
| **Transaction and attachments** | Create the import graph and source mapping within one destination transaction. Enable and verify foreign keys per connection outside the transaction. Verify counts and invariants and write the import marker in the same transaction. Keep managed evidence at its original relative path. Retain valid legacy rebase, raw URL, raw path and ordering. Mark missing or unsafe legacy references as unresolved with provenance. Unresolved bytes cannot be manufactured. Never make untrusted or out-of-root paths eligible for cleanup. Copying or relocating bytes is a later staged operation with digest validation. |
| **Post-import verification and cutover** | Reopen SQLite and check integrity, FK constraints, the source fingerprint and completed import status. Compare record, target and tombstone accounting, a field-level value digest, evidence states/hashes where readable, and legacy query/selection checks. Commit the imported graph with a pending-verification status, then activate the new writer with an authoritative SQLite marker only after all checks pass. On restart, a pending marker resumes verification and an active marker opens SQLite directly. No dual-write path. |
| **Recovery and rollback** | Before successful activation, recover from the untouched source with a known intact snapshot. An interrupted pre-commit import leaves no authoritative rows. Retry with the same source fingerprint and mapping, or rebuild staging from the verified source. A previously completed import is detected and never appended again. After activation and especially after new writes, SQLite is authoritative. A raw source snapshot is historical. Stop writes on an integrity incident, preserve the current database and successfully staged evidence, and use verified destination recovery or forward repair. Never downgrade silently to stale data. |
| **Future portable backup** | Essential internal recovery protects migration. A user-facing backup/restore interface may follow. Reserve a versioned manifest contract with portable IDs, historical layout and choice revisions, typed values, tombstones, settings intended for transfer, managed originals and explicit unresolved references. Keep entitlement verification independent. A closed or coordinated SQLite backup is required for a live store, especially if write-ahead logging is used. A PDF/ZIP report or naked database file is insufficient for cross-device record and file restoration. [SQLite backup documentation](https://www.sqlite.org/backup.html) |

A failed preflight must leave both the raw source and managed files readable. For a source the old app can read, keep the old workflow available under the source authority or give a clear retry route. If the source itself cannot be loaded safely, show a recovery state with intact originals and non-sensitive diagnostics. This contract preserves accountable data through the migration, but post-cutover device loss or physical damage requires backup coverage beyond this task.

## 7. Migration and parity acceptance matrix

**Fixture construction.** Construct synthetic SharedPreferences key maps with stringified records matching `CpdEntry.toMap()`. Add hand-authored raw rows for malformed data and unknown keys that the standard encoder cannot generate. Create uniquely identifiable synthetic photos and multi-page PDFs in a temporary app-like Documents tree, with ordinary files, URLs, absent originals and aliased paths. Use the existing converters/search and current report selection as oracles for valid records. Store normalised report expectations and hashes, avoiding assertions on random paths or PDF timestamp bits. Run each fixture from a fresh directory and test separate app-container roots. Use no real records.

| Fixture | Required automated assertion | Manual or integration check |
|---|---|---|
| Standard entries and optional values | Every raw row maps once. Title/details, missing-to-empty legacy defaults, credited minutes including explicit zero, and every attachment ordinal equal the expected result. Existing edits cannot overwrite unknown or historical values. | Add/edit and revisit default CPD form on both platforms. Confirm validation, headings and date formatting. |
| Multiple professions, targets and restored/deleted rows | Associations, active/deleted counts, case rules, orphan recovery and all target period totals match. Recovering a profession or record preserves explicit consent boundaries. | Rename, remove, restore and compare home and list summaries. |
| Identical-looking records and duplicate ID anomalies | Distinct stable identities, predictable legacy ID/ordinal ordering and zero collapsed entries. Before commit, ambiguous targets surface a verifiable diagnostic. | Check equal-title/date evidence in PDF and ZIP. |
| Unicode, unusual filenames, multiline, empty and optional fields | Byte-equivalent text survives, searches match Unicode titles/details/evidence strings, and field applicability stays distinct from a blank. No invalid archive paths. | Check readability with localised dates, languages, long titles, multiline text and CSV import into a spreadsheet. |
| Calendar and duration edge cases | Calendar date examples, leap day, zone offsets, date limits, explicit zero and legacy rounding expectations proven. Export endpoints inclusive and target end-exclusive. Raw invalid or fractional inputs survive with an explicit decision. | Repeat with affected timezones and date preferences on devices. |
| Multiple files, images, PDFs and shared originals | Reference count, order and SHA-256 match for every readable original. PDF rendering/fallback, URL manifests and original packaging match expected artefacts. Removing one association leaves a shared asset available. | Open and share image/PDF/other on both devices. Review a multi-page evidence PDF and companion ZIP. |
| Missing, external, invalid or out-of-root references | Raw references survive and unresolved states are observable. No URL fetch or out-of-root delete during import. ZIP/PDF handles unrenderable evidence. | Confirm explanations and relinking/recovery expectations for unresolved references. |
| Historical layouts and choices | Label/order changes retain IDs and old rendering context. Old records retain populated retired choices and evidence. A retroactive blank creates no bulk values. A future-only field appears on a newly created backdated record. | Open an old record in the editor and verify requiredness, restore and export semantics. Later editor gate when implemented. |
| Corrupted JSON, unknown extensions, incomplete rows and conflicts | Manifest accounts for every raw row. Preserve the uninterpreted remainder. An unsafe exception aborts activation with recoverable originals and no silent skip. | Confirm retry and recovery UI and privacy-safe error summaries. |
| Interruption, repeated attempts and low disk | Inject failure before snapshot, during transaction, after transaction/marker, before activation and after activation. Reopen and rerun. Exactly one authoritative store, no duplicate identities and no lost evidence. Test changed source fingerprint and incompatible schema. | Force-close or terminate on supported iOS and Android; verify device restart, retry and storage failure. Test already-activated records with newer writes. |
| Search and all exports | Input IDs, dates, sorting and attachment projections match source. Assert semantic PDF content and page/evidence artefacts, row/column CSV contract and a manifest/byte comparison for ZIP. Compare selection even when UI filters are active. | Open each export and share it via the existing sheet. Inspect evidence, fallback notices and first/last dates. |
| Equipment portability | A module-only or test adapter consumer can apply and revise the equipment layout, store, search and project it for export with no CPD imports. | Exercise the generic editor screens later and confirm no CPD navigation, mandatory credit or past-only date policy appears. |

**Release pass/fail.** All active, deleted, duplicate and unsupported rows must be accounted for with zero unexplained value changes and zero destructive side effects. Every readable original must remain available and byte-identical unless the user initiated a separate authorised change. Every expected old query and export must match its documented semantics on supported devices. Any dropped data, partial authoritative commit, missing target, broken restoration, silent quarantine or unrecoverable failure is a cutover failure. Existing tests remain regression oracles, including [profession recovery](../../../test/repositories/profession_recovery_test.dart), [form behaviour](../../../test/widgets/add_entry_page_test.dart), [selection](../../../test/utils/export_selection_test.dart), [attachment resolution](../../../test/utils/export_attachment_test.dart), and [PDF document tests](../../../test/utils/cpd_pdf_document_test.dart).

## 9. General Record Keeping reuse assessment

| Equipment field | Generic type and example |
|---|---|
| Equipment identifier | Short text · PUMP-042 |
| Equipment description | Long text · North pump, loading bay |
| Inspection date | Date-only · 19 November 2026 |
| Inspection result | Single controlled choice · Pass, Needs follow-up, Out of service |
| Maintenance notes | Long text · Seal replaced, no leak |
| Technician | Short text · É. Malik |
| Supporting photographs or documents | Ordered managed attachment references · photograph and inspection PDF |
| Next inspection date | Date-only · 19 February 2027, with future dates allowed |

The General Record Keeping host creates an eight-field user recipe, applies it to independent collections and prompts with the same field UI. The module saves values by stable field identity and records the layout revision. Editing notes updates the current values, and retiring a result choice leaves the historic label accessible. Search uses the equipment ID, technician and resolved choices. A generic report projection contains the date, result and original evidence references. The host decides date format and output labels. There are no hours, targets, profession IDs, store grants or regulatory checks in this example. The disposable Dart probe validates the value shape and resolution. Real reuse still requires implementing and testing that agreed boundary.

**Assumptions that would break reuse.** A mandatory credited-duration column, forced past-only dates, a CPD type in repository or report signatures, a global 20-field constant in the domain, evidence paths tied to the CPD sandbox, or category names treated as field policy. Keep them in host configuration or port adapters. Cross-app transfer of a user's data is a separate portable-format and consent workflow.

## 11. Remaining risks and final approvals

| Risk | Control before activation |
|---|---|
| Driver and OS SQLite differences | Use conservative SQL and test exact Flutter, sqflite and OS matrix. Host tests support the design with no mobile compatibility guarantee. |
| Hidden legacy data variation and multiple writers | Read raw keys non-mutatingly. Stage before activation. Close all mutation paths over one repository and review actual source-use inventory. |
| Misinterpreted dates, fractional time or unknown extensions | Carry raw values and require classified mapping. Treat the observed decoder behaviour as a legacy oracle plus a signal for ambiguous fixtures, rather than a universal normalisation rule. |
| File lifecycle across migration, reports and cleanup | Keep bytes in place, preserve managed/missing distinctions and use reference-aware staged cleanup. Validate recovery snapshots and container path changes. |
| Legacy export differences and premature generic API | Preserve CPD selection/rendering via a compatibility projection, run semantic output comparisons and enforce a non-CPD test before considering extraction. |
| Deferred full backup | Internal recovery addresses cutover. Set expectations for device loss and long-term restoration separately. Approve package and portable user backup when there is a concrete consumer or release requirement. |

**Approve before Phase 1 starts**

1. Use the locked sqflite driver, an internal plain Dart module and one repository writer. Confirm the supported mobile matrix and minimum-device checks as a gate.
2. Approve the stable identities, canonical bindings, immutable history and sparse values. Confirm original historical label/order and the separate permanent-deletion rule.
3. Approve raw source classification, who resolves ambiguous data, retention of raw and internal recovery snapshots, interrupted migration handling and post-cutover recovery. Approve the proposed minimum 30-day internal snapshot window and defer user-facing backup UI.
4. Approve exact first-release parity and the test gates. Initial types are text, dates, durations and evidence. Plan choice compatibility now and authorise editor/template rollout separately.
5. Approve the staged sequence, with cutover only after the native and synthetic migration rehearsal and actual parity gates. Keep purchases, advanced scheme reporting and package extraction outside Phase 1.

**GO WITH CONDITIONS.** Proceed only after architectural approval. The first implementation should verify the already-installed driver on the target devices, then establish the generic model and recovery fixtures. Authorise production migration only after legacy parity, evidence integrity, interruption/retry and recovery checks pass.
