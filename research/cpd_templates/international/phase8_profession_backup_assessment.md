## Proposed backup and restoration protocol

1. **Create Backup** in the existing profession menu captures one stable collection graph and its reachable originals. Include active and recoverable deleted records, stable source IDs, retained custom and retired fields, field and choice revisions, layout history, original evidence relationships, profession-scoped targets and reporting periods, report settings and pinned recipes and rules. Include the profession's branding asset and configuration when supported. Use the collection ID for scoping. The CPD adapter must resolve mixed legacy namespaces such as name-keyed targets or report selections into scoped data. Exclude unrelated professions, raw whole-installation migration inventory, global preferences, local authority markers, purchase grants, cached store receipts and drafts. The generic layer receives collection metadata and opaque, versioned host extensions, so General Record Keeping can reuse it. CPD rules and purchases stay in the CPD host.
2. **Verify and save.** Use a consistent read snapshot and pin referenced immutable originals while streaming. Reuse the existing container with an explicit scope and a distinct payload version. Its validated metadata should include source lineage, archive identity, UTC creation time, profession name, record counts and evidence inventory. Establish a digest and length when accepting new originals. For legacy originals with an existing independent digest, compare against it. For originals without a trusted prior digest, verify the bytes read and archived and make no claim about earlier damage. Record unavailable evidence explicitly by type and reference. Permit a backup of remaining data only after the user reviews and explicitly accepts the missing or damaged items. If an expected payload is truncated, disappears or fails digest verification during creation or import, stop and report the failed verification. Keep link references without fetching external targets. Offer save or share through a system provider after verification. Report verification separately from provider handoff or cancellation. Purge only app-owned temporary copies once handoff completes or an abandoned attempt is safely reconciled.
3. **Choose and inspect.** Add **Restore from Backup** to the shared onboarding and Home profession-creation screen. Select the external file read-only. Check schema and scope, bounds, structure, graph, immutable versions, evidence and digests before exposing any tile or mutating the live database. Show the original profession name, backup date, record count with any deleted records identified, attachment count with separate original, link and unavailable figures, and verification status. For example, **Verified · 2 attachments unavailable at backup** distinguishes a valid partial snapshot from a damaged file. Bind import to the reviewed seal. Recheck the seal if reopening the file or continue from the very same verified private stage. Cancel and failure leave the source file available.
4. **Resolve identity.** Create a fresh local collection ID. Remap record, attachment and other collection-owned IDs where required, together with their references and host keys. Retain original IDs and lineage as provenance. Reuse shared definitions and template/rule revisions only after an exact semantic match. Reject incompatible content under the same immutable ID and version in the first release. Use an operation receipt and lineage check under the commit transaction, so repeated taps, filename changes, re-exports and restart cannot duplicate a tile. For an already present lineage, show the existing or recoverable tile and stop, even if the second archive is newer. If only the name collides with an unrelated active or deleted profession, offer a new name using the existing validator. Keep merging, replacing and deliberately cloning an existing lineage outside this proposal. Confirm how a user can restore again after intentionally purging an earlier import.
5. **Add atomically.** Before confirmation, state that restoration adds a separate tile. After confirmation, preflight capacity and recheck name, lineage and versions at commit. Use fresh managed paths and finalize verified originals before any database references can commit. Commit the collection graph, scoped metadata and import receipt in one SQLite transaction. On first launch, completion must follow a durable import receipt and resume the existing creation flow. Reconcile interrupted staging from that receipt. Before commit there is no visible tile. After commit a retry returns the same tile. Delete or quarantine only proven unreferenced files owned by the attempt. Success, cancellation and failure should preserve unrelated professions, purchases and the chosen external file.
6. **Keep ownership separate.** Restore historical record values, layouts, evidence, selected periods and rule pins even when the paid template cannot be verified on this device. Allow access to the user's records and evidence and the ordinary export path. Gate new template adoption, paid editing, updates and premium report actions through existing CPD entitlement checks. A backup does not issue a grant or activate a catalogue product. Offer store restoration separately. File verification establishes integrity. Publisher authenticity has a separate trust check. Treat retained rules as historical data, validate them using supported calculators, and keep the current verified bundled catalogue or a separately approved external channel in charge of template distribution.

## Ordinary saves and upgrade recovery

**Recommend SQLite's own journal plus durable original-file publication.** The current repository enables foreign keys, and the Phase 8 rehearsal explicitly configures `DELETE` journalling with `synchronous=FULL`. Keep the transaction boundary and assess `DELETE` with `EXTRA` on the minimum native engines before selecting it for production. SQLite documents the extra directory sync at commit and a possible last-transaction rollback after power loss with `DELETE/FULL`. Consider `WAL/FULL` only if measured concurrency warrants WAL lifecycle management. Never turn off journalling to avoid extra files. [Repository](../../../lib/recording_engine_storage/sqlite_recording_repository.dart) · [SQLite journalling and synchronous modes](https://www.sqlite.org/pragma.html#pragma_synchronous)

Reuse the managed-file staging pattern. Flush and hash the original, publish it under a unique same-volume path and qualify the native directory durability barrier before committing the file reference. Keep original files immutable while records or recoverable history reference them. A failed SQL transaction can leave a staged or unreferenced file, which startup reconciliation can check without copying the database or evidence. Use a small per-operation receipt or intent only where reconciliation needs it. Acknowledge success only after the required files and transaction are durable. On ambiguity or corruption, preserve readable data and report the problem. An earlier migration copy must never silently replace more recent SQLite data. Journalling and reconciliation address interrupted writes and upgrades. Recovery after uninstall, device loss or unrecoverable storage damage depends on an accessible external backup containing the required data and evidence. [Managed original storage](../../../lib/recording_engine_storage/managed_attachment_files.dart)

Keep the independently verified, temporary legacy recovery snapshot, quiescent pre-import check, migration fence and restart verification. Keep a temporary pre-upgrade recovery copy when a schema migration requires it. Apply the existing minimum 30-day migration-snapshot retention from verified activation and hold cleanup while integrity or authority is unresolved. Retention expiry alone gives no authority to delete legacy originals. These safeguards apply to migration and upgrade operations only. [Migration readiness and retention](phase3b_migration_readiness.md)

Its absolute statements about data transmission and deletion should distinguish app storage from user-directed sharing and system-managed device copies. The public policy and support page, store listings and tracked app sources provided no standalone developer terms. Apple's Standard EULA is the published fallback if there is no custom EULA. Confirm the actual terms and store setup before publication. Current onboarding and Settings cover preferences and tips and have no backup guidance.
