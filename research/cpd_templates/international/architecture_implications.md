# Phase 1 architectural review · CPD Progress Tracker

**20 November 2026 · Proposed for approval · Read-only review of checkout `425e6bb`**

The [decision and feasibility report](phase1_decisions_and_feasibility.md) records the follow-up driver selection, host probes, and more detailed migration contract for approval.

## 1. Recommendation

**Keep one Flutter application and separate the recording engine inside it.** Give that engine a plain Dart domain for collections, typed records, field definitions, layout revisions and template application. Use a local transactional database for record data and managed files for original attachments. Keep profession setup, credited CPD time, targets, regulatory policy, branded report presentation and store entitlements on the CPD side of the boundary. Preserve today’s free CPD workflows through a built-in default layout. A profession template is optional, and users can maintain a general-purpose CPD log without selecting a regulatory scheme.

Design the module so a future General Record Keeping app can take the recording functionality and suitable UI components with few changes. Demonstrate this with a synthetic, non-CPD workflow before extracting a package. A future app will have its own shell, vocabulary, policies, storage and commercial rules. Code portability and user data transfer are separate decisions.

**Approve Phase 1 as a foundation and migration scope.** The evidence supports the migration architecture and reusable model now. Commercial demand, exact regulator handoffs and some rule changes still need validation before approval of a template or scheme report. ## 3. Dependency boundaries and package strategy

```text
CPD app shell
  navigation, purchases, legacy grants, styling, mobile pickers
  ├─ reusable Flutter form/editor widgets
  │      └─ recording engine
  ├─ CPD policy and reports
  │      └─ recording engine and resolved record data
  └─ local storage, file and export adapters
         └─ recording engine contracts
```

Keep the domain free of Flutter context, native plugins, app localisations, store products and scheme names. Implement it as concrete domain objects and operations for record validation, layout editing, field resolution and generic projection. Use a narrow repository boundary for loading and committing whole operations, a managed file boundary for evidence, and a report snapshot handed to writers. Inject those at the app’s composition point. A separate abstraction for every table, global event bus, arbitrary plugin system or general rule language would add overhead without a second consumer.

| Reusable recording functionality | CPD-owned policy and presentation |
|---|---|
| Collections, typed field values, generic record CRUD, soft deletes, searchable field definitions, ordered layouts, saved user templates, import validation, queries, evidence references and report snapshots. | Calls a collection a profession, supplies its default form, binds canonical activity date and time, enforces CPD entry rules, computes user targets, resolves profession branding and registers CPD catalogues. |
| Reusable form field presenters, draft configuration, accessibility, reorder controls, options and search widgets. Platform adapters supply file pickers, permission prompts, links and sharing. | Chooses entry points, copy and brand styling, editor entitlements, training QR behaviour and whether the CPD field limit of 20 is active for a collection. |
| Generic portable data format, PDF/CSV projection and managed original-file bundle. | CPD report title, profile, formats and legal context; optional scheme rule evaluation, approved official handoff guidance and purchase restore. |

| Packaging option | Practical trade-off |
|---|---|
| **Internal modules now · recommended** | One build and test setup while the API is being learned. Change boundaries cheaply during legacy parity work. Enforce the dependency direction through imports and an isolated portability test. |
| Local shared Dart or Flutter package now | The package manifest and public surface provide stronger compile-time boundaries. They also bring versioning, test setup and dependency coordination while the second product’s needs are unknown. A mixed Flutter package can prematurely entangle UI and storage. |
| Copy or extract after unstructured feature growth | Fastest initially. CPD types, file paths, localisations and reports become spread across the engine, making later reuse expensive. |

Extract the plain Dart domain first when a second real consumer or a clear build constraint justifies it. Extract Flutter widgets separately if they share enough behaviour. Keep the repository and file adapters together with the app while they have one user, with clear imports so the implementations can move later. No package publication is needed to share code between two apps. [Flutter package guidance](https://docs.flutter.dev/packages-and-plugins/developing-packages)

**Portability test.** Use a synthetic *equipment maintenance* collection with a future inspection date, status, notes and photos. Save a user template, apply it to another collection, change a choice, reload historical records, search and export. The test must need no profession model, CPD date restrictions, forced credited time, CPD copy, regulator registry or purchase provider. A later General Record Keeping app can supply its own limits and default layouts. Its application sandbox will have its own storage. Moving data across products, if approved, requires an explicit compatible export/import workflow, with attachment bytes and user consent.

## 4. Proposed data and authority model

Model relationships now. Confirm exact SQL names and driver during authorised technical planning. **Use SQLite behind one local repository as the working choice.** Keep entity IDs as stable portable strings and legacy integers as migration provenance and legacy ordering keys. Use relational metadata and indexed record headers. Store ordered layout and choice snapshots in compact, versioned structured payloads where that simplifies a layout revision. Use sparse typed field-value rows and explicit file-reference rows. Prefer straightforward indexed queries. Add typed search projections or full-text indexing when measured needs justify them. Enable and verify foreign keys on connections, and restrict deletion where history or file references exist. [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html)

| Model | Identity and relationship |
|---|---|
| **Collection** | Stable collection ID, editable display name, lifecycle state and current layout revision. CPD uses a collection as a profession tile. Renaming or deleting the display container does not create a new identity. |
| **Record** | Stable record ID, collection ID, creation layout revision, technical creation/modification data, deletion state and concurrency revision. Keep the legacy integer/sort key where present. Business dates and durations use bound fields. |
| **Field instance and revision** | Stable field ID scoped to the collection. Each layout snapshot has ordered configurations referring to those IDs, with label, type, requiredness, help, validation, choice version, presentation and optional provenance. Position, name and type label are never identity. |
| **Field value** | At most one sparse value per record/field pair. Store supported type and exact semantic payload, or ordered evidence links for attachments. Preserve absence, explicit zero/false, and inapplicability as separate states. An unknown future type remains recoverable or blocks import safely. |
| **Choice set/version** | Stable options with independent IDs and revision-specific labels/status. Duplicate text labels do not merge values. The historical choice selection keeps enough scope and version to resolve meaning after retirement. |
| **Evidence asset and link** | Managed asset ID or external/unresolved reference with display name, storage state, media metadata and optional integrity hash. An ordered link connects it to the record and evidence field. One asset can have several references. Use references to originals and file bytes outside the database. |
| **Catalogue definition/version** | Reusable, stable catalogue ID with human labels, terms, type, rules, choices and applicability/source metadata. Insertion creates an independent collection field with a copy of effective settings and optional source provenance. |
| **Template/version** | Versioned recipe containing ordered field definitions and supported defaults, with template-local stable field keys and optional product-side provenance. Source distinguishes built-in, curated and user-owned layouts. Recipe contains no personal record values, logo, files or purchase token. |
| **CPD collection settings** | CPD-owned bindings, target minutes/cycle, optional scheme and role selection, and optional branding preference by collection ID. Store ownership and legacy grants in separate app-level entitlement state. |
| **Scheme rule and report context** | CPD-owned rule identifier and version with effective range, authority/source, applicable roles, approved input bindings and fixtures. A report snapshot records the exact context used and which values were considered eligible or unresolved. |

**One authoritative value per CPD binding.** Seed legacy fields for activity date, title, details, credited duration and evidence. Bind stable role keys for CPD screens and totals. Date and credited duration remain protected in CPD layouts. Store a calendar day and integer minutes. If date or minutes are projected for sorting/querying in SQLite, update the projection in the same transaction and treat it as rebuildable. The generic engine has no mandatory activity date or duration. A generic due date can be in the future. Preserve legacy display ordering and the CPD rule requiring title or details for the standard form.

**Initial types.** Short and multiline text can share a text value representation. Date uses a calendar-day type, and duration stores exact integer minutes. File and photograph are managed evidence configurations. Model single-select and bounded multi-select with the same stable choice references so later additions do not redesign historical storage. Exact decimal quantities carry an explicit unit. NMC participatory time is a duration subset, ACCA units are derived only under the applicable policy, and California contact hours and CORU credits are distinct awarded quantities. Resolve launch type scope separately. Defer computed-field scripting, arbitrary nested forms and configurable taxonomies until an approved use case requires them. [Field type recommendations](../field_type_recommendations.md)

## 5. Editor, templates and versioning

The [Phase 4 implementation report](phase4_recording_configuration.md) records the current storage and version rules. The internal engine now supports layout drafts, exact decimal values, versioned library prototypes, anchored section headings and bundled or user template metadata. The production entry form and storage authority are still separate. The stage numbers in this review reflect the original planning sequence.

### Editor compatibility

Reuse the existing form tiles and typed presenters for entry, read-only detail and safe illustrative previews. The editor gives each full tile a dedicated handle and menu, with keyboard and screen-reader reorder paths. Labels, requiredness, help, formatting and choices operate on a draft. Search the Field Library by terms, category and scope. Preview the definition, configure a copy, choose historical applicability, then insert into the draft. Save checks the expected current revision and the resulting active count before committing. CPD centrally enforces **20 active fields**, including standard fields. Retired history and logos sit outside the count. Cancel or a failed commit preserves prior layout and data. [Edit Fields UI specification](../../../docs/custom_fields_ui.md)

Start with existing text matching and a small offline search over labels, aliases and resolved choice labels. Search catalogue definitions separately from user records. Use stable field keys in structured filtering and canonical date ranges in CPD. For older records preserve original evidence references and display labels needed for search. Avoid content indexing inside sensitive files.

### Version axes

| Version | Rule |
|---|---|
| **Database and interchange schema** | Advance storage and portable-format compatibility independently. Detect unsupported versions before changing destination data. |
| **Catalogue and choice set** | New version updates the defaults for new insertions. Rename/reorder keeps option IDs when meaning is stable; semantic changes create new IDs. Retired options remain visible in past records and exports. |
| **Template recipe** | Publish immutable versions under the same applicable product. Applying a template copies the reviewed version into a profession layout. Later versions are explicit choices. A user can save an independent recipe from scratch or from an editable layout. Remap field IDs when applying to another collection, preserving canonical bindings. Never automatically export its personal values or assign a regulatory profile through lookalike field labels. |
| **Collection layout revision** | A local atomic commit creates the next revision. Existing records retain their creation revision. A deliberate extension for earlier records is represented by applicability metadata rather than a bulk write of empty values. |
| **CPD policy/rule version** | Independently version evidence eligibility, effective periods, role thresholds, rolling summary rules and rounding. Keep historic definitions and clarify when a regenerated report is using a newer rule. No silent retrospective recalculation. |

**Recommended historical resolution.** Start with a record’s creation revision, then add fields explicitly applied to its historical cohort. For **future records only**, use a creation revision boundary even when the new activity is backdated. Apply that rule to restorable records as well. Preserve the creation-time label/order for historical interpretation and report reproduction, with current layout labels available where explicitly desired. Retain populated retired fields and evidence in historical views and exports. When a replacement type would change meaning, assign a new field ID and preserve the old type and values. Draft validation and report readiness are separate, so a newly required field with no historical value does not block an unrelated edit. Display historical choice values even after they can no longer be selected for new records.

**Application and commercial boundaries.** Templates default to future records. Reusing an owned template on multiple tiles creates independent layouts. A user-created recipe can be used without a professional template product. In CPD, editing or creating layouts follows Custom Fields rights, including verified legacy paid-app users. Template-only ownership allows applying the fixed predefined layout and editing record values. Eligible library definitions do not grant managed template updates or scheme reporting. Keep the existing **£3.99 template** and **£12.99 Custom Fields** one-time proposal and the broader logo eligibility unchanged. Entitlement loss locks eligible future actions while preserving the user’s records, existing layouts and usable standard exports. The engine does not read purchase state or apply these CPD policies itself.

## 6. Safe migration and data recovery

[Phase 3B](phase3b_migration_readiness.md) implements the startup decision and its recovery rules. A write-once marker outside the attempt directory precedes the bound SQLite receipt. A pending or ambiguous handoff stops both writers. The generic engine owns the authority decision and cold preservation. CPD owns inventory, validation and interpretation. Normal production startup remains on the existing store until separately approved.

**Use one authority at a time.** Run migration behind a single guarded startup/recovery path. Preserve original preferences and attachments through a validated cutover. After cutover, all record, profession, target and evidence association writes use the destination. Earlier binaries read stale preferences, so recovery after new writes must use the destination snapshot or a validated forward repair. Copying the legacy snapshot back would discard new work.

1. **Inventory and snapshot.** Read the raw legacy preferences without invoking helpers that rewrite or sanitise data on read. Inventory active and deleted professions, targets, all JSON entries, counter, and attachments. Record recoverable originals or plain diagnostics without logging sensitive text or paths. Capture a recoverable snapshot before enabling destination writes. Use synthetic or separately authorised fixtures.
2. **Resolve before committing.** Map legacy names using the current normalisation where unambiguous. Keep recoverable orphan groups and original name provenance. If there are duplicate record IDs, preserve each raw row with a distinct stable mapped ID or hold it for review. Use source position and provenance for ties rather than deduplicating implicitly. For malformed rows and conflicting targets, preserve the original input and require a recoverable handling path. Do not mark migration complete while data cannot be faithfully represented.
3. **Import atomically.** Create default layout revisions for each collection and migrate record values, targets and tombstones together. Preserve date/calendar behaviour and exact total minutes. Retain original date data for ambiguous formats. Keep an idempotent source identity and completion marker in the same destination transaction. Attachments can point to existing managed files during this change. Preserve raw URLs, app-relative paths, known absolute Documents paths and explicit unresolved references, including ordering and duplicates. Do not move or recompress original files during initial cutover.
4. **Verify and switch.** Compare mapped record values and disposition, legacy counts, relevant targets, dates, restore state, search and export selection, and evidence resolution. If the process is interrupted before commit, retry with consistent IDs. If it restarts after commit, recognise the destination as authoritative. Database changes can be atomic. File copying, backup and cleanup need staged operations and recovery tests.
5. **Provide recovery.** Move failed migrations into a clear recovery state with an actionable diagnostic and preserved data. Never silently create an empty library. Define snapshot retention and an operator or user recovery path. The existing share ZIP is a report. Any future portable backup needs layout, variants, historical values, managed originals, unresolved references and an integrity manifest. A store restore validates ownership separately.

**Evidence safety.** For new copies, stage managed files, finalise the bytes, then commit their database references. Reclaim abandoned staged files only when safe. On explicit historical purge, remove references transactionally and recheck all references and active report snapshots before deleting an app-owned asset. Preserve shared originals and deleted-but-restorable record evidence. Missing bytes stay visible as missing. Require safe relative import paths, size limits and preview of conflicts, and defer merging datasets until a conflict policy is approved. Neither a legacy external path nor a file outside the managed asset directory is eligible for cleanup.

### Release acceptance for an authorised migration

| Check | Pass condition |
|---|---|
| Count and content parity | Every active/deleted record is exactly accounted for, including duplicates and ambiguous rows. Titles, multiline details, dates, duration, ordered evidence links, profession/target association and recovery state round-trip. Evidence originals used for parity are byte-identical. |
| Legacy workflow parity | Create, edit, QR/picker attachment, search, rename, delete/restore and weekly/monthly/yearly targets behave as expected. Standard export uses the same search-filtered record set, inclusive date boundaries and deterministic order. Explicitly test leap days, device timezone changes and target boundary semantics. |
| Export/evidence parity | Test standard, evidence and ZIP outputs with images, a multi-page PDF, unsupported files, URLs and missing evidence. Check page readability, links, same-name files/records, selected originals and the existing fallback behaviour. Verify conventional CSV columns and multiline/locale handling for any later structured format. |
| Interruption and recovery | Simulate low storage, unreadable/malformed entries, terminated migration before and after commit, repeat launch and app upgrade with changed container paths on the intended iOS and Android minimums. The source remains recoverable and a retry introduces no duplicate rows or orphaned file deletes. |
| Layout history | Rename, reorder and retire an option or field, apply a field to an earlier cohort, create a backdated new record, replace a type, and restore a soft-deleted record. Confirm existing data survives, and a stale draft cannot overwrite a newer revision. |
| Independence and privacy | Run the equipment example without CPD dependencies. Use synthetic data and avoid collecting record content or file names for diagnostics. Approval of migration and recovery lies outside this review. |

## 7. Reporting and import/export

**One selection, then separate interpretation and rendering.** Record queries build an immutable snapshot of selected records, resolved fields, evidence references and applicable layout metadata. The CPD host supplies date bindings, names, standard profile and optional premium logo. General reports render rows and values from the snapshot. A separate CPD calculation step can take the snapshot plus an explicit scheme rule, role, date window and independently verified inputs, then return totals, exclusions, unknowns and review notes. Use small tested calculators for approved schemes. There is no general rules editor requirement.

Keep an export snapshot consistent if a field, file reference or logo changes during rendering. Continue passing the same record selection to standard PDF, evidence PDF, CSV and original bundle. Reuse the current PDF preparation/render separation and evidence fallback. A generic document projection can provide headings, field values and attachment references without embedding CPD branding, localisations or policy. Preserve canonical date and precise units in machine-readable outputs. For CSV, decide an explicit format version, stable column identifiers, protection against spreadsheet formula evaluation and mapping for repeating options. Maintain the legacy CSV format until a replacement is approved.

Scheme-specific reports are opt-in. NMC needs participatory and total minutes over the right cycle. HCPC needs learning mix, personal outcomes and selected evidence. GDC needs role-specific years, verifiable status, adjacency across cycles and output rounding. These are separate from ordinary totals. Attach a report’s rule version, reference period and inputs used so later regeneration can explain a difference. Official submission, signatures, portfolio-level declarations and external rule feeds require separate approval. Missing proof needs a visible warning. Future grouped reports should preserve profession contexts and use neutral cover branding, with section logos only where appropriate. [Reporting requirements](../reporting_requirements.md)

**Import and backup.** Keep the CPD legacy importer in a CPD adapter. A generic portable interchange format could use a versioned manifest for collections, definitions, choices, records, evidence and original bytes. Phase 1 needs a recoverable migration snapshot and an agreed boundary for future interchange. User-facing import, round-trip restoration across apps, record merging and official upload should follow separately reviewed acceptance criteria. Verify an official import workflow before claiming compatibility.

## 8. Risks, alternatives and decisions

| Issue | Recommendation and alternative |
|---|---|
| Storage implementation | SQLite is the working recommendation for local transactions and reference integrity. A mobile-first direct driver such as sqflite has lower setup cost but requires explicit SQL/migrations and another route for targets beyond its main platform plugin. Drift offers typed access and migration tooling with build/code-generation overhead. Validate driver support, supported SDKs, migrations and on-device evidence IO before locking it in. Upgrading SharedPreferences APIs alone would retain the whole-list and cross-key write problem. [sqflite documentation](https://pub.dev/packages/sqflite) · [Drift documentation](https://drift.simonbinder.eu/) |
| Dynamic storage shape | Prefer relational identities, bounded layout snapshots and sparse values. A JSON blob per record is simpler initially but makes selective writes, field-level references and filter indexes harder. Fully normalised tables for every option/validation property add migration overhead. Keep SQL projections small and verify with realistic data. |
| Migration and release recovery | Prioritise a tested local recovery route before activating the new writer. A dual-write transition adds split-authority risk. A generic import/merge or cloud sync would widen the problem without establishing migration safety. |
| Extraction timing | Start with one module boundary and a portability test. Packaging becomes a practical next step when the second app can test that boundary. Keep CPD fallbacks and templates from leaking into shared types. |
| Regulatory maintenance and trust | Maintain dated rules and fixtures per approved scheme, with clear readiness and official handoff language. The 60 research entries are a review pool. Publish a limited versioned catalogue and explicit updates when approved. |

### Decide now, before implementation

1. **Boundary and scope.** Approve internal, CPD-independent modules with the non-CPD portability test, a local-only Phase 1 and a defined platform support matrix. Decide whether portability initially means code reuse only or whether a user-facing backup/restore release must accompany migration.
2. **Storage and identifiers.** Approve SQLite as the target family and the logical model. Select a supported driver after an authorised compatibility check. Approve stable IDs, one writer, canonical CPD bindings without duplicate values, and any indexed projections.
3. **History and versions.** Approve creation-revision and historical-extension behaviour, original historical label/order strategy, explicit template adoption and option retirement. Confirm requiredness for older records and the policy for incompatible type changes and explicit purge.
4. **Migration and recovery contract.** Agree treatment of duplicate/ambiguous data, unknown paths and malformed values, snapshot scope and retention, cutover/rollback rules and the acceptance fixtures above. Determine who can resolve any case the app cannot map safely.
5. **Parity boundary.** Approve unchanged standard CPD entry, target, delete/recovery and export behaviour as the first release gate. Agree baseline data types and preparation for evidence identity, controlled choices and exact units without exposing editor or report features prematurely.

### Safely defer

- Package extraction, shared Flutter widget distribution and launch design for General Record Keeping.
- Exact physical schema tuning, full-text search, cloud sync, app accounts, remote catalogue delivery and arbitrary user rules.
- User-facing cross-app import or merge, structured report schema, multi-profession packs and branded export UI.
- Full Field Library publication, commercially sold profession templates, shop, store restore, verified legacy grants and any special scheme reports. Each needs separate authorisation and validation. Record core and paid access remain independent.

## 9. Recommended implementation sequence after approval

| Stage | Scope and exit condition |
|---|---|
| **1A · Foundations and migration design** | Confirm platform/driver, identity and version contract, file lifecycle and safety fixtures. Prove recovery behaviour on synthetic legacy input and exercise a non-CPD record through the domain and repository before enabling production migration. |
| **1B · Legacy-compatible cutover** | Route existing app workflows through the new repository and CPD adapter, preserve standard layout, totals and all export modes. Release only after parity, interruption, recovery and device tests. |
| **2 · Configurable recording** | Deliver the separately approved draft editor, user-created templates, historical applicability and curated offline Field Library. Exercise the non-CPD portability fixture and historical export cases. |
| **3 · CPD additions** | Independently authorise commercial entitlements, branding, reviewed profession templates and individual scheme reports. Test international roles and pilot NMC/HCPC only after current authority and practitioner validation. |
| **4 · Separate product** | When a General Record Keeping prototype exists, consume the internal boundaries and extract the appropriate domain or widget package. Evaluate whether structured user export/import is needed and validate it independently. |

**Approval recommendation.** Approve an internal plain Dart recording engine, transactional local storage, stable versioned identities, a CPD adapter that preserves the free app, and a recovery-tested migration. Use the five decisions above to define implementation scope. Require legacy parity and a non-CPD domain test for Phase 1, then exercise the full editor-to-export portability workflow once those features exist. The commercial and regulatory layers can follow their own approvals. This review changed documentation only. No tests or builds were run and no migration was started.
