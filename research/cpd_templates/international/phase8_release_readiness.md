## Verification for this review

- **Flutter:** 258 automated tests passed. Formatting and `git diff --check` passed. `flutter analyze --no-pub` reported the same 13 existing findings (one warning, 12 informational), including two in unrelated local marketing output. None were in the changed Dart files.
- **Native debug:** iOS 18.5 simulator and Android API 24 and 34 emulators passed the scoped-restore checks. The API 24 run exposed default WAL journalling on the temporary review database. The candidate now uses a verified standalone rollback journal during rebuild and is subsequently opened read-only. The rehearsal's active recording store still uses its platform-compatible durability configuration.
- **Safeguards:** Test cases reject wrong passwords, damaged plain or protected files, unsupported future framing and row schemas, value or layout tampering, invalid report settings, forged entitlement state, invalid attachment references and a changed candidate or unexpected journal. Failed inspections leave no restorable preview or added profession. The widget test verifies the forgotten-password warning and cancellation cleanup. Owned originals published before an interrupted transaction remain subject to the exclusive cold-start reconciliation; the earlier stop-and-restart test passed on iOS 18.5 and API 24. Platform handoff caches need the physical checks below.
- **Backward compatibility:** The current verifier read plain and password-protected v2 archives from `bbdb9c5` in both directions between iOS 18.5 and Android API 24. The internal v1 whole-store test and migration-authority test also passed on iOS 18.5. Archive fixtures contained synthetic records only. The scoped test confirmed that historical fields, evidence and ordinary export data remain available without a grant and that the archive confers no new paid access.
- **Performance:** In the five-record fixture with two available originals, the plain and protected backups occupied 8.43 MB each. Create / protect and copy / repeated restore checks took 0.20 / 0.45 / 1.42 s on iOS 18.5, 1.83 / 3.67 / 12.06 s on API 24, and 2.09 / 3.62 / 13.97 s on API 34. Sampled process memory was approximately 637, 374 and 411 MB respectively, including the entire debug Flutter process. These runs do not establish signed release, physical-device, real low-storage or large-evidence performance.

Safeguards and test probes are in `d1c172b`. [Format and fixture retention contract](backup_format_compatibility.md)

## A. Must resolve before production SQLite activation

1. **Signed migration and authority on physical devices.** After separate approval, exercise the current supported iOS 15.6 and Android API 24 baselines and one current physical reference device per platform. Use dedicated synthetic profiles under the approved upgrade identities. Verify existing and fresh apps, quiescent source capture, independent snapshot and hash checks before import, persistence after restart, and original data accessibility. Test invalid or ambiguous rows, corrupted and missing originals, low storage, external interruption at file publication/SQL commit/authority update, verified migration resume, and no repeated onboarding. Honor the established minimum 30-day post-activation retention and reserve any deletion decision for separate verification. [Migration authority procedure](phase3b_migration_readiness.md#physical-device-verification-procedure)
2. **No loss of existing functionality.** Compare free CPD, historical edits, targets, deleted items, search, QR and attachment paths, normal and evidence exports, CSV, ZIP and report sharing/printing under the new authority. Validate saved IDs, field choices and record meanings against the original. Any parity deficit on an existing path blocks cutover even if a new premium feature can wait. An invalid backup, missing store or legal notice cannot obstruct access to prior records or ordinary exports.
3. **Recovery and capacity under real use.** Prove durable SQLite commit and owned-original publication across supported filesystems. A crash before commit may leave only app-owned staging that a later exclusive start can reconcile. On ambiguity preserve the only data copy and stop for recovery. Review sustained low-space operation, recovery storage, writer fencing, performance and safe support instructions. Record exact time, device, OS, build, free bytes and before/after graph and evidence checks. Require explicit approval to change the activation flag.

## B. Must resolve before public release of the revised features

1. **Real commerce and customer recovery.** Verify both approved non-consumable products with store-localised pricing, pending/declined purchases, account changes, reinstalls, replacement devices, offline views and refunds. Prove original paid-app grants survive recovery through an approved method and that a synthetic, migrated or restored backup never becomes store authority. Approve support handling for customers who cannot retrieve old proof.
2. **Backup and premium feature qualification.** Test archive handling, temp file lifecycle and interrupted handoff with physical iOS Files, Android document providers and representative recipient apps. Review encryption, optional password/cleartext wording and OS backup exclusions. Qualify legacy rules against expected ordinary and premium report results and keep a versioned archive regression corpus. Release only reviewed templates and supported report actions. Keep the renderer guard until the complex-script verification gate is met.
3. **Full user journeys and legal review.** Run VoiceOver and TalkBack across welcome, restore, interrupted setup, field editing, template preview, purchase verification, report generation and recovery. Review native sizing, colour, contrast, error copy and six supported locales. Approve the privately held Terms and Privacy drafts and notices, local agreement receipt behaviour, trader identity, store policies, privacy declarations and purchase disclosures. Set real effective dates and approve which terms apply to existing users. [Proposed agreement and notice behaviour](../../../docs/custom_fields_ui.md#14-terms-privacy-and-release-readiness-review)
4. **Release sign-off.** Document device results and residual limits under both distribution identities, and review them with the owner before any public submission. The simulator and emulator runs do not satisfy physical-device or signed-store verification.

## C. Can safely follow a qualified release

- Expand the template catalogue and scheme-language translations once the first selected template is reviewed and its maintenance ownership is established.
- Consider selective adoption UI beyond the required supported-version behaviour, remote template distribution, and richer library organisation. Preserve historical rules and saved data before offering upgrades.
- Reconsider time-based trials only with separate authorisation and clear store-specific terms. Free sample previews already support evaluation without starting a timed entitlement or risking real records.
- Revisit deferred commercial experiments and report formats once evidence supports demand. Any issue affecting a capability already offered to users remains in A or B.

## Store verification protocol for a later approved test

**Current result.** No legitimate paid transaction or original paid-app grant was restored in this review. The branch uses rehearsal fixtures and has no live StoreKit or Play Billing purchase implementation or approved store test catalogues. The tests establish that archives cannot grant access and that historical data remains usable when verification is unavailable. Production readiness still requires the following signed/store tests.
