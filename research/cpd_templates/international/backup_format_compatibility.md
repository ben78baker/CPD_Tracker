# Profession backup compatibility contract

**22 November 2026 · Phase 8 review.** Persisted archive formats, template recipes and rule versions are durable user data. Compatibility changes need review independently of SQLite application schema upgrades.

## Published-format candidates and version pins

| Layer | Current contract | Required future treatment |
| --- | --- | --- |
| Encryption envelope | `RCEBAK01`, fixed Argon2id and AES-256-GCM parameters, authenticated header, ordered 64 KiB frames and authenticated EOF | Keep the exact decoder. Use a new envelope marker for changes to KDF, ciphers or framing. Authenticate every frame before releasing a candidate and reject unsupported or corrupted input. Current ciphertext also protects names, values and evidence. |
| Portable framing | `RECBAK01`, explicit manifest version, counts/lengths and SHA-256 digests, ordered payloads and bounds | Keep a bounded read-only decoder for each supported version. The internal version 1 whole-store archive remains separate from the user-facing single-profession workflow. A version 1 archive cannot replace or merge public data; qualify a separate conversion tool only if an actual user-facing format requires it. |
| Single-profession payload | Manifest version 2 with explicit collection scope and logical row schema 4. Includes source lineage and a verified graph of definitions, layouts, records and evidence with a closed allowlist for host settings | Keep schema 4 as a frozen wire representation. Dispatch an older manifest and schema through an explicit decoder and mapping. Do not equate the current SQLite schema number with the wire schema. Reject newer versions before a live write with an explanation to use a compatible app version. |
| Historical semantics | Stable field and instance IDs, original layout and explicit retrospective additions, immutable controlled values and versions, template recipes and rule pins, CPD period/target/report settings | Resolve records through their recorded layout revision. Preserve definitions, versioned choices and report rules embedded in the backup, including versions missing from the current catalogue. An absent supported calculator revision is a compatibility issue to explain, not permission to apply new rules silently. |

The v2 writer and reader now bind schema 4 explicitly. Before changing any live table, explicitly maintain the schema 4 logical encoder or version the payload. The current implementation uses matching table shapes and a bounded reader for schema 4. There is no converter for an unrealized future schema. Bind the reviewed candidate to its closed database digest and check for unexpected SQLite journals. Open it read-only when applying the restore. Verify records against their own effective fields and verify evidence independently.

## Maintainer migration procedure

1. Before changing schema or semantics, capture small synthetic plain and encrypted fixtures for every user-facing released version. Keep test passwords public and fixture content synthetic. Include historical choices, records added before and after a layout change, retrospective additions, retired fields, deleted records, partial and complete evidence, CPD periods, target and report choices. Preserve fixtures independently of the new writer and record their hashes and originating versions.
2. Decode with the original bounded parser into a private candidate. Verify immutable pins, record-local field applicability, ownership and references. Apply explicit transformations into the current schema before showing preview. Verify the transformed graph again. Preserve original source identity, meaning and evidence bytes. Unknown or ambiguous values stay recoverable in the original file and produce an explanation in the app.
3. Compare old and new semantic projections, period results, ordinary historical exports and evidence digests. Test across both mobile platforms, including files originating on the other platform and a future unsupported format. Compare the old file's bytes before and after. Any database restoration is additive and goes through the existing duplicate and entitlement boundaries.
4. Keep old readers and calculation rules while supported files require them. If a version cannot be supported, leave the original archive intact, explain the limitation at inspection and provide a separately approved recovery or conversion path before retiring its reader. Do not overwrite an old encrypted or plain copy in place.

An older published SharedPreferences installation follows the independently verified legacy migration workflow, including quiescent backup and fail-closed authority. It does not emit version 2 profession archives. Migration snapshots and profession backups have separate purpose and retention.
